#### Features Implemented:

  - Added `MQTTClient` interface with `Publish(topic, payload)` method
  - `GatewaysHandler` now accepts `MQTTClient` parameter
  - `Update()` handler publishes to `sys/command/reload/{gateway_id}` after successful gateway update
  - MQTT publish errors are silently handled (don't fail HTTP request)

- Updated `internal/handlers/tags.go`:
  - `TagsHandler` now accepts `MQTTClient` parameter
  - `Update()` handler publishes to `sys/command/reload/{gateway_id}` after successful tag update
  - Uses the gateway_id from the tag to determine which driver to reload

#### How It Works:
1. When a gateway is updated via `PUT /api/gateways/{id}`:
   - Gateway is updated in PostgreSQL
   - core-api publishes `"reload"` payload to `sys/command/reload/{gateway_id}`

2. When a tag is updated via `PUT /api/tags/{id}`:
   - Tag is updated in PostgreSQL
   - core-api publishes `"reload"` payload to `sys/command/reload/{tag.gateway_id}`

3. Driver services (already implemented in US-012 and US-015):
   - Subscribe to `sys/command/reload/{gateway_id}` topic
   - On receiving reload message, reload gateway config and tags from PostgreSQL
   - Update internal tag map without stopping polling loop
   - New tags are added, removed tags are deleted from polling

#### Design Decisions:
- MQTTClient interface allows dependency injection and testing
- MQTT publish failures don't fail HTTP requests (API resilience)
- Drivers already have non-blocking reload channel to prevent duplicate reloads
- Simple "reload" string payload - drivers just need to receive the message

### 2026-01-24 - Historian Deadband Filtering (Iteration 16)

#### Completed User Stories:
- **US-023**: Implemented historian deadband filtering

#### Features Implemented:
- `services/engine-historian/main.go` - Enhanced with deadband filtering functionality
- PostgreSQL connection for querying tag configuration (historize, historize_deadband)
- New structs:
  - `TagInfo` - Holds tag ID, Historize flag, and HistorizeDeadband value
  - `PreviousValue` - Stores previous value in Redis for comparison

#### Deadband Filtering Logic:
1. **Tag Info Lookup** (`getTagInfo`):
   - Queries PostgreSQL via JOIN across organizations → sites → areas → gateways → tags
   - Matches by hierarchy names (org, site, area, gateway, alias) using case-insensitive comparison
   - Caches results in Redis for 1 hour (key: `tag_info:{org}:{site}:{area}:{gateway}:{alias}`)
   - Returns tag ID, historize flag, and historize_deadband value

2. **Historize Check**:
   - If `tag.historize` is false, data is skipped entirely (not stored in InfluxDB)

3. **Deadband Comparison** (`shouldStoreValue`):
   - If deadband ≤ 0, always store (filtering disabled)
   - Retrieves previous value from Redis (key: `prev_value:{tag_id}`)
   - First value always stored (no previous to compare)
   - Compares with new value using deadband threshold

4. **Value Comparison** (`exceedsDeadband`):
   - Supports float64, int, and bool value types
   - For numeric types: `|new_value - previous_value| >= deadband`
   - For boolean: any change stores the value
   - Uses `math.Abs()` for proper absolute difference calculation

### 2026-01-24 - Alarm Database Persistence (Iteration 23)

#### Completed User Stories:

#### Database Functions:

1. **insertAlarmRecord()** (line 435-443):
   - Inserts new alarm events into `alarms` table
   - Parameters: tag_id, state, message, triggered_at
   - Query: `INSERT INTO alarms (tag_id, state, message, triggered_at) VALUES (...)`

2. **updateAlarmToClear()** (line 445-464):
   - Updates most recent ACTIVE alarm to CLEAR state
   - Sets `cleared_at` timestamp
   - Uses `ORDER BY triggered_at DESC LIMIT 1` to find the ACTIVE alarm
   - Logs warning if no ACTIVE alarm found (idempotent)

#### Alarm Event Persistence:

1. **ACTIVE Event** (`transitionToAlarm`):
   - Converts timestamp from milliseconds to `time.Time`
   - Calls `insertAlarmRecord(tagID, AlarmStateActive, message, triggeredAt)`
   - Creates new row with state=ACTIVE, triggered_at=now

2. **RTN Event** (`transitionToRTN`):
   - Converts timestamp from milliseconds to `time.Time`
   - Calls `updateAlarmToClear(tagID, clearedAt)` to update existing ACTIVE row
   - Updates previous ACTIVE row to state=CLEAR with cleared_at timestamp
   - Calls `insertAlarmRecord(tagID, AlarmStateRTN, "Return to normal", clearedAt)`
   - Creates new row with state=RTN for the return to normal event

#### Database Schema:
```sql
CREATE TABLE alarms (
    id SERIAL PRIMARY KEY,
    tag_id INT NOT NULL REFERENCES tags(id),
    state VARCHAR(20) CHECK (state IN ('ACTIVE', 'RTN', 'ACKNOWLEDGED', 'CLEAR')),
    message TEXT,
    triggered_at TIMESTAMPTZ NOT NULL,
    acknowledged_at TIMESTAMPTZ,
    cleared_at TIMESTAMPTZ
);
```

#### Alarm Event Flow:
1. Alarm triggers → INSERT row with state=ACTIVE
2. Value returns to normal → UPDATE ACTIVE row to state=CLEAR + INSERT new row with state=RTN
3. All alarm events are queryable via database for historical analysis
